# M4 — Chaos harness and report

## What we built and why
`chaos/harness.py` runs the agent thousands of times, kills it, restarts it and checks invariants (`chaos/invariants.py`); `chaos/bench.py` measures overhead; `chaos/report.py` writes `docs/EVAL_REPORT.md` and the README table from `results/`.

## Key concepts (with code)
- **Kills**: half of first attempts are killed by a timer at a random moment (`plan_kill` → `run_attempt` sends SIGKILL); half at a targeted kill point via `AGENTWAL_KILL_AT` (`chaos/killpoints.py`). Each restart is killed again with probability 0.3; at most 10 restarts.
- **Invariants**: (1) payments in SQLite == intended refunds, once each (`check_effects`); (2) output == uninterrupted reference (`comparable`); (3) records acknowledged before the kill survive (`acked_records_survive`, using the journal's ack sidecar); (4) no `NonDeterminismError`.
- **Power loss per fsync policy**: suites `aw-pl-*` use `PowerLossJournal`. With a deterministic model even `none` stays correct (the deterministic key + idempotent receiver absorb the lost journal) but re-bills LLM calls; with a sampled model `none` breaks: a lost `LLM_RESULT` is re-sampled, the new amount is sent under the old key, the receiver rejects it. That is what fsync is buying you.
- **Receiver assumption**: `aw-noidem` (retry, no dedup) duplicates exactly in window ③; `aw-reconcile-noidem` doesn't.
- **Torn writes**: `aw-torn` truncates the journal at a random byte after every kill.

## Verify it yourself
```bash
make chaos-smoke                       # 50 runs, ~10 s

```

## Interview questions
1. **How do you know a kill really happened at the point you claim?** Targeted kills are the agent SIGKILLing itself inside the hook at that point (exit code −9 checked by the harness). For random kills the harness records the last durable journal record at the kill (`landed_at`), which shows which windows they hit.
2. **Your AW suite shows zero duplicates. What would make it fail?** A receiver that ignores keys (shown by `aw-noidem`), agent code that's non-deterministic outside the journal, or losing the intent while the effect happened *and* changing the request on retry (shown by `aw-pl-none-stoch`). Zero violations is evidence under the stated assumptions, not a proof.
3. **How did you test what fsync protects, given kill -9 can't?** By swapping in a journal that keeps un-fsynced records in user space, so a kill loses them like a power cut, and running the suite under each policy.

## Break-it exercise
Remove the `self.journal.sync()` after the intent in `DurableContext._effect` and change `aw-pl-always-stoch` to use `fsync="group:8:5"`. Rerun that suite. Predict first: which invariant breaks, and in which window?
