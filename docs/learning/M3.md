# M3 — Demo agent, mock payments service, baselines

## What we built and why
- `demo/agent.py`: a refund batch agent over 10 tickets (`demo/tickets.py`), runnable as `aw`, `b1`, `b0`.
- `demo/fake_model.py`: free deterministic "LLM" (keyword rules, small sleep, billing log). `--stochastic` samples amounts like a real model at temperature > 0.
- `demo/local_model.py`: free local LLM via Ollama (`qwen3:8b` by default, `AGENTWAL_OLLAMA_MODEL` to change). It samples, so its decisions vary between runs — the journal must cope with that.
- `demo/payments_service.py`: a separate process with SQLite that honours `Idempotency-Key`, offers `GET /payments?key=`, and can turn deduplication off.

## Key concepts (with code)
- **B0 naive** (`run_b0`): no state. A crash restarts the batch; every refund before the crash is paid again.
- **B1 checkpoint-after-step** (`run_b1`): an atomic, fsynced checkpoint after each ticket — what many frameworks do. **Why it still duplicates**: the checkpoint is written *after* the payment. A crash between the two (window ③) restarts that ticket, and the retry has no key, so the payment happens twice. It also re-bills the LLM call of the interrupted step.
- **AW**: the intent with a deterministic key is durable *before* the payment, so the retry is recognisable.
- **Same kill points for all strategies**: the baselines fire the same hook names (`HookedLLM`, `hooked_tool`) so the comparison is fair.
- **Fairness note**: B1 + a deterministic key per ticket would also avoid duplicates for this agent. What it still lacks is the journaled LLM output (re-billing and, with a sampled model, a different decision on retry) and a general mechanism for agents whose steps aren't a fixed list.

## Interview questions
1. **Why doesn't checkpointing after every step give exactly-once effects?** Because the effect and the checkpoint are two separate actions. Any crash after the effect and before the checkpoint makes the restart redo the effect. Making the checkpoint more frequent shrinks the window but never closes it; you need a record *before* the effect plus an idempotent receiver.
2. **Why is the payments service a separate process?** A `kill -9` of the agent must not take the "outside world" with it; in reality the payment provider keeps going. It also means a request can be applied by the service even though the agent died before reading the response — the case that matters.
3. **What does the 409 on a reused key with different parameters protect against?** A bug or non-determinism that sends a different charge under an old key. Silently returning the old payment would hide the mismatch; Stripe-style rejection surfaces it.
