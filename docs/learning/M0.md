# M0 — Research and design

## What we built and why
A one-page comparison of how Temporal, DBOS and LangGraph survive crashes (`docs/DESIGN.md` §1) and the ADRs for the record format and fsync policy (`docs/DECISIONS.md`). The point was to borrow a proven model rather than invent one: **replay the code, read every non-deterministic input back from a log, and make side effects idempotent**.

## Key concepts
- **Durable execution**: a run's progress lives in durable storage, not in the process. A crash loses the process, not the progress.
- **Event history + replay (Temporal)**: rerun the workflow code; every command it emits is compared with the history. Mismatch = nondeterminism error. AgentWAL: `src/agentwal/replay.py` (`ReplayIndex.match`).
- **Step checkpoints (DBOS)**: store each step's output; on restart skip steps that have one. AgentWAL's `LLM_RESULT`/`EFFECT_RESULT` are exactly this.
- **At-least-once + idempotency = effectively once**: all three systems retry an interrupted side effect and ask you to make it idempotent.

## Interview questions
1. **How does Temporal know where to resume?** It doesn't "resume" a stack; it re-executes workflow code from the start and feeds it the recorded results of completed activities/timers from the event history, so the code deterministically reaches the point where history ends. New commands after that point are executed for real.
2. **Why must workflow code be deterministic but activities need not be?** Workflow code is re-executed on every replay and its commands are compared with history; any branch on time/random/IO could take a different path and no longer match. Activity results are recorded once and then read back, so their non-determinism is captured.
3. **DBOS checkpoints step outputs in Postgres. What happens if a step crashes after its side effect but before the checkpoint?** The step is retried on recovery, so the side effect runs again. That is why DBOS says steps must be idempotent — the same window AgentWAL calls ③.
