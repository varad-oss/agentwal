# M2 — Durable context and replay

## What we built and why
`durable_run` and `DurableContext` (`src/agentwal/context.py`): journaled LLM calls, two-phase effects, journaled `now/random/uuid`, and non-determinism detection (`src/agentwal/replay.py`).

## Key concepts (with code)
- **Replay by sequence number**: every journaled operation takes `seq = _next_seq()`. If the journal has a completed entry at that seq, return its recorded result; the first incomplete one runs for real (`_llm_call`, `_effect`, `_value`).
- **Why replay requires determinism**: replay reruns your code and assumes it makes the same calls in the same order. If a decision depended on something not journaled (wall clock, `random`, a dict ordering, a changed prompt), the code issues a different request at some seq; the recorded result would be applied to the wrong question. The request hash catches it → `NonDeterminismError` naming both requests.
- **Two-phase effects**: `EFFECT_INTENT` (durable) → call tool with key `aw:{run_id}:{seq}` → `EFFECT_RESULT` (durable). An intent without a result is ambiguous; recovery either retries with the **same key** (`recovery="retry"`) or asks `reconcile(key)` first.
- **Exactly-once delivery vs exactly-once effects**: after a crash in window ③ the agent cannot know whether the request or only the response was lost (the Two Generals problem in miniature) — so it must resend, i.e. delivery is at-least-once. If the receiver deduplicates by key, applying the effect is idempotent, so the *effect* happens exactly once.
- **Cost**: an `LLM_RESULT` in the journal means that call is never paid again. Only a crash mid-call (`llm_mid`) re-bills.

## Interview questions
1. **Walk me through recovery of a crash after the payment but before the result was journaled.** On restart the code replays; all earlier calls return recorded results. At the payment's seq the journal has an intent with no result. AgentWAL resends the same request with the same idempotency key; the payments service finds the key and returns the original payment instead of charging again; AgentWAL writes the result and continues. With `reconcile`, it first does `GET /payments?key=` and writes the found payment as the result without calling POST.
2. **Why is exactly-once delivery impossible but exactly-once effects achievable?** The sender can't distinguish a lost request from a lost response without another round trip, which can also be lost — so it must retry and some messages arrive twice. If the receiver remembers keys it has applied and treats a repeat as a no-op returning the original result, duplicates are harmless: delivery at-least-once + idempotent receiver = effect exactly once.
3. **What happens if someone adds `random.random()` to the prompt?** The first run journals `LLM_CALL` with hash H1. After a crash the replay builds a different prompt with hash H2 at the same seq; `ReplayIndex.match` raises `NonDeterminismError` showing both. Fix: use `ctx.random()`, which is journaled.
