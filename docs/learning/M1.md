# M1 — Journal and recovery

## What we built and why
An append-only journal (`src/agentwal/journal.py`) of CRC-checked records (`src/agentwal/records.py`) with three fsync policies and torn-tail truncation, plus a fault-injecting `PowerLossJournal` that makes `kill -9` behave like a power failure.

## Key concepts (with code)
- **Framing**: `[length][crc32][type][json]` — `records.encode`. Length tells you where the record ends; CRC tells you whether it is whole. `records.scan` stops at the first record that fails either check.
- **Torn tail**: a crash mid-`write` leaves a partial record. `Journal.__init__` scans, `ftruncate`s to the last valid record and fsyncs the truncation, so later appends never follow garbage.
- **written vs synced**: `os.write` puts bytes in the OS page cache (survives a process crash). `fsync` forces them to the device (survives power loss). `Journal.written_count` / `synced_count`.
- **What fsync guarantees**: when it returns, the data (and on most systems the needed metadata) is on stable storage. On macOS plain `fsync` does *not* flush the drive's own cache; `F_FULLFSYNC` does (`FsyncPolicy(full=True)`, spec `always+full`). Creating a file also needs an fsync of the directory (`_fsync_dir`).
- **Why `kill -9` can't test fsync**: the kernel keeps the page cache when a process dies, so un-fsynced data is still read back after restart. To test fsync you must lose the page cache — `PowerLossJournal` keeps un-fsynced records in user space so they die with the process.
- **Group commit**: one fsync for several records (`group:N:MS`). Barriers (`append(..., barrier=True)`) force the fsync for records that must be durable before the outside world is touched.

## Interview questions
1. **Why a CRC per record, not a checksum of the whole file?** Records are appended over time; a per-record CRC lets recovery find the exact last good record and keep everything before it. A whole-file checksum would only say "something is wrong".
2. **What does `fsync` guarantee and what doesn't it?** It guarantees the file's written data has been handed to stable storage before it returns. It does not order writes across files, does not make a new file's directory entry durable (fsync the directory), and on macOS doesn't flush the disk's write cache (needs `F_FULLFSYNC`). It says nothing about data you haven't written yet.
3. **Why can't `kill -9` test durability, and how did you test it?** A killed process's writes are already in the kernel's page cache, which survives; only an OS crash or power loss drops it. I simulated that with a journal that buffers un-fsynced records in user space, so `kill -9` loses exactly the un-fsynced suffix, and ran the chaos suite under each fsync policy.
