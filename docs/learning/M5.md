# M5 — Docs and demo

## What we built and why
README (results table generated from `results/`), the Mermaid diagram of intent → effect → result with crash windows (`docs/DESIGN.md` §4), `make demo` (kill-and-resume script, transcript in `docs/demo_transcript.txt`), `python -m agentwal.dump` to inspect a journal.

## Key concepts
- **Explain the windows from the diagram**: ① intent written not fsynced, ② intent durable before the call, ③ effect done before the result, plus `llm_mid`. For each: what's in the journal after recovery, what replay does, why it's exactly-once (table in `DESIGN.md`).
- **Honest scoping**: AgentWAL is a study of durable execution, not Temporal/DBOS. Single process, single file, no workers, no versioning beyond `code_version`.

## Interview questions
1. **Draw the crash windows and explain each recovery path.** (Use the diagram; for ③ say "intent with no result → same key → receiver returns the original payment, or reconcile finds it".)
2. **What are the assumptions behind "no duplicated side effects"?** The receiver deduplicates by idempotency key or offers a lookup by key; the agent's code is deterministic outside the journal; the key is derived the same way on every retry; the journal's intent is durable before the effect (fsync barrier; true unless policy `none`).
3. **How is this different from LangGraph checkpoints?** Checkpoints save graph state between steps; an interrupted step is re-run, so side effects inside it can repeat unless you add idempotency yourself. AgentWAL journals inside a step — each LLM call and each effect, with an intent before the effect — so resume is at the granularity of a single call.
